## 1.2 <span style="color: rgb(36,91,219); background-color: inherit">VeRL</span>

VeRL 用 HybridFlow 组织 RLHF 的跨模型数据流和分布式执行。理解框架前，先把模型角色、计算阶段和并行约束对齐。

### 1.2.1 <span style="color: rgb(36,91,219); background-color: inherit">RLHF 流程</span>

RLHF 通过对给定 prompt 生成的候选回答进行排序的方法，将 LLM 的语言空间和人类价值观对齐。RLHF 一般包含多个模型，如：<span style="color: rgb(220,155,4); background-color: inherit">策略模型</span>**`Actor`**<span style="color: rgb(220,155,4); background-color: inherit">、价值模型</span>**`Critic`**<span style="color: rgb(220,155,4); background-color: inherit">、参考模型</span>**`Reference`**<span style="color: rgb(220,155,4); background-color: inherit">，以及奖励模型 </span>**`Reward`**。

![](../../images/视觉多模态项目-image.png)

<span style="color: rgb(100,37,208); background-color: inherit">策略模型和参考模型都是经过预训练或微调的 LLM</span>，一般来说是 SFT 后准备要 RLHF 的模型；<span style="color: rgb(100,37,208); background-color: inherit">价值模型和奖励模型是基于人类偏好数据集微调的其他 LLM</span>，token 预测头被替换为标量输出头。

以 PPO 为例，一次 RLHF 迭代拆成生成、准备和训练三个阶段：

> * **<span style="color: rgb(36,91,219); background-color: inherit">第一阶段（生成）</span>**：策略模型针对一批 prompt 生成对应的 response
>
> 🍀 * **<span style="color: rgb(36,91,219); background-color: inherit">第二阶段（准备）</span>**：利用 prompt 和生成的 response，<span style="color: rgb(100,37,208); background-color: inherit">价值模型计算其价值，参考模型计算其参考对数概率，奖励模型计算其奖励值</span>。这些操作均通过各自模型的一次前向传播完成
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">第三阶段（训练）</span>**：使用前两个阶段产生的数据和损失函数，通过 Adam 优化器更新策略模型和价值模型

其他 RLHF 算法也基本遵循类似的三阶段流程。例如，<span style="color: rgb(220,155,4); background-color: inherit">Safe-RLHF 引入了一个辅助预训练损失，并增加了一个成本模型，用于拟合人类偏好和安全性标签；ReMax 引入额外的生成步骤以降低方差，并在数据流中移除了价值模型</span>。

<span style="color: rgb(100,37,208); background-color: inherit">LLM 一般采用</span>**<span style="color: rgb(100,37,208); background-color: inherit">数据并行</span>**<span style="color: rgb(100,37,208); background-color: inherit">、</span>**<span style="color: rgb(100,37,208); background-color: inherit">流水线并行</span>**<span style="color: rgb(100,37,208); background-color: inherit">和</span>**<span style="color: rgb(100,37,208); background-color: inherit">张量并行</span>**<span style="color: rgb(100,37,208); background-color: inherit">方式进行训练和推理服务</span>。在数据并&#x884C;**`DP`**&#x4E2D;，<span style="color: rgb(100,37,208); background-color: inherit">输入数据被划分为多个子集，每个子集由不同的 GPU 处理</span>。**`ZeRO`**&#x662F;内存优化的数据并行训练方案，可逐步在多个 GPU 上分片存储优化器状态、梯度和模型参数。流水线并&#x884C;**`PP`**&#x548C;张量并&#x884C;**`TP`**&#x5219;<span style="color: rgb(100,37,208); background-color: inherit">将模型参数、梯度和优化器状态分布在多个 GPU 上</span>。目前<span style="color: rgb(100,37,208); background-color: inherit">比较常用的分布式训练框架如</span>**`Megatron-LM`**<span style="color: rgb(100,37,208); background-color: inherit">和</span>**`MegaScale`**<span style="color: rgb(100,37,208); background-color: inherit">使用</span>**`3D`**` 并行`。在 3D 并行中，**<span style="color: rgb(100,37,208); background-color: inherit">PP</span>**<span style="color: rgb(100,37,208); background-color: inherit"> 规模表示模型训练中的流水线阶段数量，</span>**<span style="color: rgb(100,37,208); background-color: inherit">TP</span>**<span style="color: rgb(100,37,208); background-color: inherit"> 规模表示张量被划分的份数，</span>**<span style="color: rgb(100,37,208); background-color: inherit">DP</span>**<span style="color: rgb(100,37,208); background-color: inherit"> 规模表示模型副本的数量</span>。LLM 推理系统在部署时也采用类似 3D 并行的方式，但仅对模型参数和 KV 缓存进行分片。

在 RLHF 数据流中，不同模型可能执行不同的计算任务，包&#x62EC;**<span style="color: rgb(100,37,208); background-color: inherit">训练</span>**<span style="color: rgb(100,37,208); background-color: inherit">（</span>**<span style="color: rgb(100,37,208); background-color: inherit">一次前向</span>**<span style="color: rgb(100,37,208); background-color: inherit">+</span>**<span style="color: rgb(100,37,208); background-color: inherit">一次反向传播</span>**<span style="color: rgb(100,37,208); background-color: inherit">+</span>**<span style="color: rgb(100,37,208); background-color: inherit">参数更新</span>**<span style="color: rgb(100,37,208); background-color: inherit">）、推理（</span>**<span style="color: rgb(100,37,208); background-color: inherit">一次前向传播</span>**<span style="color: rgb(100,37,208); background-color: inherit">）和生成（</span>**<span style="color: rgb(100,37,208); background-color: inherit">多次前向传播的自回归生成</span>**<span style="color: rgb(100,37,208); background-color: inherit">）</span>。具策略模型执行训练和生成任务，价值模型执行训练和推理，参考策略模型和奖励模型仅执行推理任务。<span style="color: rgb(46,161,33); background-color: inherit">针对不同类型的任务，可以为不同模型应用不同的并行策略，以实现最优吞吐量</span>。

### 1.2.2 <span style="color: rgb(36,91,219); background-color: inherit">分布式执行</span>

**<span style="color: rgb(222,120,2); background-color: inherit">单控制器模式</span>**<span style="color: rgb(222,120,2); background-color: inherit"> </span>**<span style="color: rgb(222,120,2); background-color: inherit">Single-Controller</span>**

<span style="color: rgb(100,37,208); background-color: inherit">使用一个集中控制器来管理整个分布式程序的执行流程。用户可以在单一进程中构建数据流的核心功能</span>，如下图，而控制器自动创建分布式工作节点执行实际计算。由于控制器拥有全局硬件和数据流图视图，因此能够灵活高效地协调资源分配和任务执行顺序。但是<span style="color: rgb(216,57,49); background-color: inherit">所有控制消息都需要从控制器发送到各个工作节点，在大规模集群上运行复杂数据流图时，这种集中调度会带来显著的通信开销</span>。

![](../../images/视觉多模态项目-image-1.png)

**<span style="color: rgb(222,120,2); background-color: inherit">多控制器模式 Multi-Controller</span>**<span style="color: rgb(222,120,2); background-color: inherit"> </span>

<span style="color: rgb(100,37,208); background-color: inherit">每个设备拥有自己的控制器</span>。现在比较好的分布式 LLM 训练与推理系统一般都采用多控制器架构，因为有良好的可扩展性和较低的调度开销，<span style="color: rgb(100,37,208); background-color: inherit">一般控制信息通过高速</span>**`PCIe`**<span style="color: rgb(100,37,208); background-color: inherit">链路在 CPU 和 GPU 之间传递</span>。如下图，每个模型运行独立的程序，同一模型的所有工作节点执行相同的代码。每个节点仅掌握局部系统状态，需通过点对点通信与其他模型协调执行顺序，图中用蓝色代码和箭头表示。

在这种架构下实现 RLHF 流程，<span style="color: rgb(216,57,49); background-color: inherit">开发者必须手动在每个设备的程序中集成集体通信、计算逻辑和点对点数据传输代码，导致计算与数据传输逻辑深度嵌套，难以开发、维护和优化</span>。例如每个模型执行本地计算&#x548C;**`all_gather`**&#x64CD;作，而<span style="color: rgb(216,57,49); background-color: inherit">策略模型还需显式地向评价模型和奖励模型发送数据，后者则必须在程序的特定位置实现接收操作</span>。

![](../../images/视觉多模态项目-image-2.png)

### 1.2.3 <span style="color: rgb(36,91,219); background-color: inherit">系统约束</span>

**<span style="color: rgb(222,120,2); background-color: inherit">异构的模型负载</span>**<span style="color: rgb(222,120,2); background-color: inherit"> </span>&#x20;

在 RLHF 中，策略模型、价值模型、参考模型和奖励模型在不同阶段分别执行训练、推理或生成任务，内存占用和计算需求各不相同。<span style="color: rgb(100,37,208); background-color: inherit">对于参考模型和奖励模型，只需在 GPU 内存中保存模型参数，因为它们仅执行前向传播</span>。而<span style="color: rgb(100,37,208); background-color: inherit">对于策略模型和价值模型，由于涉及训练过程，还需存储模型参数、梯度和优化器状态</span>。此外，为了提升对齐效果，小型策略模型（&#x5982;**`7B`**）常与更大的评价或奖励模型（&#x5982;**`70B`**）配对使用。这种<span style="color: rgb(100,37,208); background-color: inherit">异构性要求为每个模型设计差异化的并行策略和定制化优化方案</span>。

**<span style="color: rgb(222,120,2); background-color: inherit">策略模型训练和生成之间计算不平衡</span>**<span style="color: rgb(222,120,2); background-color: inherit">  </span>

在 RLHF 数据流中，<span style="color: rgb(100,37,208); background-color: inherit">策略模型的训练和生成分别对应两个节点，这两项任务通常占据每次迭代的主要时间</span>。训练阶段是计算密集型的，通常<span style="color: rgb(100,37,208); background-color: inherit">需要较大的模型并行规模，即模型被切分的数量，并将计算任务分布到更多 GPU 上</span>，例如<span style="color: rgb(220,155,4); background-color: inherit">将</span>**`7B`**<span style="color: rgb(220,155,4); background-color: inherit">模型切分为</span>**`8`**<span style="color: rgb(220,155,4); background-color: inherit">份并在</span>**`8`**<span style="color: rgb(220,155,4); background-color: inherit">个 GPU 上运行</span>。而<span style="color: rgb(216,57,49); background-color: inherit">生成阶段则是内存受限的，若沿用相同的并行策略，会导致 GPU 计算资源利用率低下</span>。一般来说<span style="color: rgb(100,37,208); background-color: inherit">结合较大的数据并行规模与较小的模型并行规模，例如</span> <span style="color: rgb(220,155,4); background-color: inherit">将</span>**`7B`**<span style="color: rgb(220,155,4); background-color: inherit">模型切分为两份并在</span>**`8`**<span style="color: rgb(220,155,4); background-color: inherit">个 GPU 上复制四次</span> <span style="color: rgb(100,37,208); background-color: inherit">，可有效提升生成吞吐量</span>。尽管为训练和生成阶段采用不同并行策略有助于提高整体效率，但<span style="color: rgb(216,57,49); background-color: inherit">在两个阶段之间动态重分片模型权重会带来显著的通信和内存开销</span>。例如，在每次 RLHF 迭代中，<span style="color: rgb(220,155,4); background-color: inherit">将</span>**`70B`**<span style="color: rgb(220,155,4); background-color: inherit">策略模型从训练切换到生成需传输高达</span>**`140GB`**<span style="color: rgb(220,155,4); background-color: inherit">的权重数据</span>，当两个阶段运行在不同设备上时，这一过程可能占单次迭代时间&#x7684;**`36.4%`**。

**<span style="color: rgb(222,120,2); background-color: inherit">多样化的模型部署</span>**

模型部署需根据其计算负载和数据依赖关系进行合理规划。如右图，<span style="color: rgb(100,37,208); background-color: inherit">部署在不同设备组上的模型可在无数据依赖的前提下并行执行；而部署在同一组 GPU 上的模型则共享显存，需按时间片依次串行执行</span>，否则并发运行多个 LLM 可能导致 OOM。

![](../../images/视觉多模态项目-image-3.png)

RLHF 各阶段存在顺序依赖，模型分开部署仍会产生 GPU 空闲。以策略模型和评价模型分组为例，训练阶段可以并行，其他阶段仍可能出现约三分之一的空闲时间。部署策略的目标不是形式上的并行，而是压缩整次迭代的关键路径并提高设备利用率。

### 1.2.4 <span style="color: rgb(36,91,219); background-color: inherit">HybridFlow 动机</span>

**<span style="color: rgb(222,120,2); background-color: inherit">多样化 RLHF 数据流图支持不足</span>**

现有 RLHF 系统普遍采用多控制器架构实现数据流。用户在实现不同 RLHF 算法时，必须<span style="color: rgb(216,57,49); background-color: inherit">处理混合了集体通信、模型计算以及点对点数据传输的复杂代码</span>。这种代码结构<span style="color: rgb(216,57,49); background-color: inherit">缺乏模块化和功能封装，导致系统与特定 LLM 框架高度耦合</span>。因此，用户不得不<span style="color: rgb(216,57,49); background-color: inherit">针对每种数据流单独实现和优化，难以复用代码且易出错</span>。目前大多数框架仅支持 PPO 算法，且因<span style="color: rgb(216,57,49); background-color: inherit">实现复杂，支持的并行策略有限</span>。例如，<span style="color: rgb(220,155,4); background-color: inherit">在</span>**`DeepSpeed-Chat`**<span style="color: rgb(220,155,4); background-color: inherit">中引入 3D 并行为训练和生成提供支持，可能需要完全重构系统，因为其代码结构高度混合</span>。

**<span style="color: rgb(222,120,2); background-color: inherit">RLHF 执行效率低下</span>**

**`DeepSpeed-Chat`**&#x548C;**`OpenRLHF`**&#x5728;策略模型训练中采用 ZeRO-3，在生成中采用 TP。OpenRLHF 在不同设备上使用不同的策略模型副本进行训练和生成，造成<span style="color: rgb(216,57,49); background-color: inherit">内存冗余和频繁的权重同步</span>。DeepSpeed-Chat 则在相同设备组上维护同一份策略模型，在训练和生成之间重新分片权重，因为<span style="color: rgb(216,57,49); background-color: inherit">两阶段并行方式不同，这对大模型仍可能带来巨大的内存和通信开销</span>。**`NeMo-Aligner`**&#x5728;训练和生成中使用相同的 3D 并行配置，导致生成吞吐率较低。



现有 RLHF 框架通常只支持一种固定的模型部署方案和执行模式。要<span style="color: rgb(216,57,49); background-color: inherit">改变部署方式极为困难，需修改模型初始化和跨节点数据传输的底层逻辑</span>。OpenRLHF 和 NeMo-Aligner 允许在准备和学习阶段并发执行模型计算，但<span style="color: rgb(216,57,49); background-color: inherit">在生成阶段，除策略模型外其他模型均处于空闲状态，浪费其所占用的 GPU 资源</span>。DeepSpeed-Chat 将所有模型共置于同一组设备上，各设备按照 RLHF 数据流顺序依次运行每个模型。当各模型负载不均衡时，这种部署方式会造成资源利用效率低下。

为克服现有系统的局限性，核心问题是：**<span style="color: rgb(100,37,208); background-color: inherit">如何设计一种灵活高效的编程模型来实现 RLHF 数据流？</span>**

<span style="color: rgb(100,37,208); background-color: inherit">在跨节点层面，单控制器架构具有明显优势</span>，因其能灵活协调不同模型之间的数据传输、执行顺序和资源虚拟化。RLHF 数据流图通常节点较少，从单一控制器向各节点发送控制消息的开销远小于节点本身所需的分布式计算开销。而<span style="color: rgb(100,37,208); background-color: inherit">在节点内部，多控制器模式因为低延迟调度能力强</span>，适合用于单个模型内部的分布式计算。

HybridFlow 采用分层混合编程：跨模型调度交给单控制器，模型内部的并行执行交给多控制器。算法数据流与底层并行策略因此可以独立调整。

### 1.2.5 <span style="color: rgb(36,91,219); background-color: inherit">框架架构</span>

主要由三个核心组件构成：**<span style="color: rgb(100,37,208); background-color: inherit">混合编程模型 Hybrid Programming Model</span>**<span style="color: rgb(100,37,208); background-color: inherit">、</span>**<span style="color: rgb(100,37,208); background-color: inherit">3D 混合引擎 3D-HybridEngine</span>**<span style="color: rgb(100,37,208); background-color: inherit"> 和</span>**<span style="color: rgb(100,37,208); background-color: inherit">自动映射算法 Auto-Mapping</span>**。如右图所示：



![](../../images/视觉多模态项目-image-4.png)

> * **<span style="color: rgb(36,91,219); background-color: inherit">混合编程模型</span>：**&#x63D0;供了一套分层 API，<span style="color: rgb(100,37,208); background-color: inherit">支持对 RLHF 数据流进行灵活表达</span>，并高效执行其中各模型的计算任务
>
> 🍀 * **<span style="color: rgb(36,91,219); background-color: inherit">3D 混合引擎</span>：**&#x4E13;为策略模型的训练与生成阶段设计，允许<span style="color: rgb(100,37,208); background-color: inherit">两个阶段采用不同的三维并行配置</span>，并在阶段切换时实现零内存冗余和最小化通信开销
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">自动映射算法</span>：**&#x6839;据 GPU 集群配置，<span style="color: rgb(100,37,208); background-color: inherit">自动确定每个模型的最优设备部署方案</span>，以最大化 RLHF 整体吞吐量

工作流程如下：

> 1. 用户启动系统时需提供以下输入信息：
>
>    1. **<span style="color: rgb(36,91,219); background-color: inherit">模型规格</span>**：包括 RLHF 数据流中策略模型、价值模型、参考模型和奖励模型的结构与规模
>
>    2. **<span style="color: rgb(36,91,219); background-color: inherit">模型部署方案</span>**：通过在给定 GPU 集群配置下运行自动映射算法获得
>
>    🍀 3) **<span style="color: rgb(36,91,219); background-color: inherit">各阶段各模型的并行策略</span>**：使用 3D 并行时的$$(p, t, d)$$元组，其中$$p$$、$$t$$、$$d$$分别表示流水线并&#x884C;**`PP`**、张量并&#x884C;**`TP`**&#x548C;数据并&#x884C;**`DP`**&#x7684;规模。
>
> 2. 单控制器程序接收这些输入后，完成以下操作：
>
>    1. 初始化 RLHF 数据流中的各个模型及虚拟资源池
>
>    2. 按照部署计划将模型或操作分发到相应设备
>
>    3. 调用运行在各设备上的多控制器函数，触发每个模型的分布式计算
>
> 3. 多控制器程序实&#x73B0;**`ParallelWorker`**&#x7C7B;，其功能包括：
>
>    1. 根据指定的并行策略，在分配的设备间构建各模型的并行组
>
>    2. 调用 3D-HybridEngine 执行策略模型的训练与生成
>
>    3. 接入 **`Megatron-LM`**、**`DeepSpeed`** 等现有 LLM 引擎，复用其他模型的训练、推理和生成能力

> 跨模型之间的<span style="color: rgb(100,37,208); background-color: inherit">数据分片由单控制器协调传输协议完成，支持不同并行策略下的数据流转</span>，包括 prompt、 response 及其他模型输出。而<span style="color: rgb(100,37,208); background-color: inherit">策略模型在训练与生成阶段之间的权重重分片则由 3D-HybridEngine 专门处理</span>。

### 1.2.6 <span style="color: rgb(36,91,219); background-color: inherit">混合编程</span>

1. **<span style="color: rgb(36,91,219); background-color: inherit">分层 API 设计</span>**

**<span style="color: rgb(222,120,2); background-color: inherit">节点内：封装分布式程序</span>**<span style="color: rgb(222,120,2); background-color: inherit">  </span>

VeRL 针对 RLHF 各阶段中每个模型的分布式计算，提供了基础&#x7C7B;**`3DParallelWorker`**。在给定设备集合的基础上，支持分布式模型权重初始化，并为每个模型建立 3D 并行组。一个并行组是一组用于承载模型某一并行维度的 GPU 集合，例&#x5982;**`TP`**&#x4E2D;的张量分片&#x6216;**`DP`**&#x4E2D;的模型副本。

![](../../images/视觉多模态项目-image-5.png)

&#x4ECE;**`3DParallelWorker`**&#x7C7B;继承，进一步提供了针对策略模型、价值模型、参考模型和奖励模型的具体模型类。<span style="color: rgb(46,161,33); background-color: inherit">每个模型类都封装了实现其分布式前向/反向传播、自回归生成以及优化器更新的 API 接口，从而将模型的分布式计算逻辑与其他模型的数据依赖解耦</span>。这些 API 可通过复用现有 LLM 的计算脚本来实现。

> **<span style="color: rgb(222,120,2); background-color: inherit">例</span>**：**`ActorWorker`**<span style="color: rgb(220,155,4); background-color: inherit">类中的</span>**`update_actor`**<span style="color: rgb(220,155,4); background-color: inherit">函数所涉及的计算逻辑，与 Megatron-LM 中的预训练脚本高度相似</span>。每个模型类封装了实现各类 RLHF 算法所需的基本操作，如策略模型类中&#x7684;**`generate_sequences`**（根据 prompt 生成 response）和奖励模型类中&#x7684;**`compute_reward`**（通过一次前向传播评估 response 质量）。

除了支持 3D 并行的`3DParallelWorker`，VeRL 还有适配 PyTorch FSDP 和 ZeRO 的基础类，分别&#x4E3A;**`FSDPWorker`**&#x548C;**`ZeROWorker`**，以及对应的模型子类，以支持多种并行策略。`ParallelWorker`就是指这些基础类。

**<span style="color: rgb(222,120,2); background-color: inherit">节点间：统一模型间的数据重分片机制</span>**<span style="color: rgb(222,120,2); background-color: inherit">  </span>

当不同模型在不同设备上采用不同并行策略时，<span style="color: rgb(100,37,208); background-color: inherit">模型间的数据传输通常涉及多对多广播</span>。VeRL 通&#x8FC7;**`@register`**&#x88C5;饰器<span style="color: rgb(100,37,208); background-color: inherit">将每个模型类中的操作与特定传输协议关联，从而统一管理此类数据传输</span>。每个传输协议包含两个函数：

> * **`collect`**：按源模型的并行策略聚合输出数据
>
> 🍀 * **`distribute`**：按目标模型的并行策略分发输入数据

上图中`update_actor`操作被注册&#x5230;**`3D_PROTO`**&#x534F;议，因为策略模型训练采用 3D 并行。在该协议中：

> 🍀 * **`collect`**&#x51FD;数将每&#x4E2A;**`DP`**&#x7EC4;的输出数据（如`update_actor`<span style="color: rgb(220,155,4); background-color: inherit">返回的损失标量</span>）收集至单控制器
>
> * **`distribute`**&#x51FD;数将输入数据（如<span style="color: rgb(220,155,4); background-color: inherit">优势值</span>）分发各&#x4E2A;**`distribute`**&#x7EC4;

数据重分片通过源模型&#x7684;**`collect`**&#x548C;目标模型&#x7684;**`distribute`**&#x51FD;数协同完成。右图展示了生成阶段的策略模型与推理阶段的价值模型之间的数据分片过程，<span style="color: rgb(100,37,208); background-color: inherit">二者采用不同的三维并行配置</span>：

![](../../images/视觉多模态项目-image-6.png)

> 🍀 1. 单控制器调用策略模型&#x7684;**`3D_PROTO.collect`**&#x51FD;数，收集数据未来对象，对应步骤 **①–③**
>
> 2. 控制器将数据发送给评价模型，对应步骤 **④**
>
> 3) 评价模型在&#x5176;**`3D_PROTO.distribute`**&#x51FD;数中将数据分发到各DP组，对应步骤 **⑤**
>
> 4) 各 GPU 根据自身的 DPP编号，从策略模型获取所需的局部批次数据，对应步骤 **⑥**

实际数据传输直接在 GPU 之间进行，避免了中心化瓶颈。VeRL 一共提供&#x4E86;**`8`**&#x79CD;传输协议，包&#x62EC;**`3D_PROTO`**、**`DP_PROTO`**、**`ONE_TO_ALL`**&#x7B49;，覆盖绝大多数数据重分片场景，当然也可通过自定&#x4E49;**`collect`**&#x548C;**`distribute`**&#x51FD;数扩展新的传输协议。

**<span style="color: rgb(222,120,2); background-color: inherit">灵活的模型部署</span>**

VeRL 提供&#x4E86;**`ResourcePool`**&#x7C7B;，用于虚拟化一组 GPU 设备。当将一个`ResourcePool`实例应用于某个模型类时，该模型的分布式计算将被映射到对应设备上。

> 🍀 * 若多个模型使用相同的`ResourcePool`实例，则它们被共置于同一组 GPU 上
>
> * 若使用不同的实例，则部署在不同设备组上

> 这里假设不同的`ResourcePool`实例之间无重叠

**<span style="color: rgb(222,120,2); background-color: inherit">异步数据流</span>**

当模型部署在不同设备组上时，一旦其输入数据就绪，执行将自动触发。<span style="color: rgb(100,37,208); background-color: inherit">策略模型的数据未来对象在控制器调用后立即返回</span>，即步骤 ①–③；<span style="color: rgb(100,37,208); background-color: inherit">控制器随即发起对价值模型的新调用，并依据传输协议分发数据</span>，即步骤④–⑤。

若多个模型共置于同一设备组，则按调用顺序串行执行。

VeRL <span style="color: rgb(46,161,33); background-color: inherit">可灵活支持多种分布式执行模式，且无需修改 RLHF 算法本身的代码</span>。

2. **<span style="color: rgb(36,91,219); background-color: inherit">不同 RLHF 算法的实现</span>**

上述 API 简化了各类 RLHF 算法的开发。只需编写少量代码，作为运行在单控制器上的单一进程程序，通过调用一系列基础 API 来触发各模型的分布式计算。

![](../../images/视觉多模态项目-image-7.png)

> 🍀 * **<span style="color: rgb(36,91,219); background-color: inherit">PPO</span>** 仅&#x9700;**`8`**&#x884C;代码，调用&#x5982;**`compute_values`**&#x548C;**`generate_sequences`**&#x7B49;模型操作，这些操作在多 GPU 上基于多控制器范式执行；
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">Safe-RLHF</span>** 在 PPO 基础上增加了一个成本模型用于评估安全性偏好，并引入预训练损失，仅需额外添&#x52A0;**`5`**&#x884C;代码；
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">ReMax</span>** 则需额外调用一次策略模型生成，并移除与评价模型相关的代码

**<span style="color: rgb(222,120,2); background-color: inherit">可扩展性</span>** &#x20;

扩展新的 RL 算法时，可以复用模型类中的分布式计算逻辑，只替换优势估计和损失函数等数值部分，例如在 `compute_advantage` 中实现 GAE，或在 loss 中加入 KL 约束。

模块化的 API 结构<span style="color: rgb(46,161,33); background-color: inherit">简化了开发流程，促进了代码复用，还能直接集成现有 LLM 训练/推理框架的代码库</span>。同时，它<span style="color: rgb(46,161,33); background-color: inherit">将模型计算与模型间的数据传输完全解耦，即使底层分布式框架发生变化，也不会影响 RLHF 算法的主逻辑代码，从而支持对每个模型的执行进行独立优化</span>。此外，系统<span style="color: rgb(46,161,33); background-color: inherit">支持根据不同负载灵活部署模型，实现 RLHF 数据流在多样化硬件环境下的最优映射</span>。

### 1.2.7 <span style="color: rgb(36,91,219); background-color: inherit">3D 混合引擎</span>

1. **<span style="color: rgb(36,91,219); background-color: inherit">并行组设计</span>**

为消除策略模型副本的冗余，**<span style="color: rgb(100,37,208); background-color: inherit">VeRL </span>**<span style="color: rgb(100,37,208); background-color: inherit">将策略模型的训练和生成阶段部署在同一组设备上，即分配给策略模型的</span>$$N_a$$<span style="color: rgb(100,37,208); background-color: inherit">个 GPU，并在这组设备上顺序执行，共享同一份模型权重</span>。但是训练与生成阶段通常采用不同的 3D 并行策略：<span style="color: rgb(100,37,208); background-color: inherit">生成阶段一般需要更小的</span>**`TP`**<span style="color: rgb(100,37,208); background-color: inherit">和</span>**`PP`**<span style="color: rgb(100,37,208); background-color: inherit">规模，但更大的</span>**`DP`**<span style="color: rgb(100,37,208); background-color: inherit">规模</span>。因此 3D-HybridEngine 支持在同一组设备上高效地进行模型参数重分片。

设$$p$$-$$t$$-$$d$$表示为训练阶段构建的 3D 并行组，对应于承载$$p$$个流水线阶段、$$t$$个张量分片和$$d$$个模型副本的 GPU 集合。3D-HybridEngine 根据训练和生成各自不同的并行策略，分别构建对应的并行组。用以下符号表示生成阶段的并行配置：

> 🍀 * $$p_g$$: 生成阶段的<span style="color: rgb(100,37,208); background-color: inherit">流水线并行组大小</span>
>
> * $$t_g$$: 生成阶段的<span style="color: rgb(100,37,208); background-color: inherit">张量并行组大小</span>
>
> * $$d_g$$: <span style="color: rgb(100,37,208); background-color: inherit">微数据并行组的规模</span>

其中，$$d_g$$表示生成阶段相对于训练阶段的模型副本倍数。也就是说，<span style="color: rgb(100,37,208); background-color: inherit">每个训练阶段的 DP 副本在生成时被拆分为</span>$$d_g$$<span style="color: rgb(100,37,208); background-color: inherit">个微</span>**`DP`**<span style="color: rgb(100,37,208); background-color: inherit">副本，用于处理</span>$$d_g$$<span style="color: rgb(100,37,208); background-color: inherit">个微批次的提示与回复</span>。

总设备数满足：

$$N_a = p \times t \times d = p_g \times t_g \times d_g \times d
\quad \Rightarrow \quad
d_g = \frac{pt}{p_g t_g}$$

<span style="color: rgb(46,161,33); background-color: inherit">微 DP 组仅在生成阶段使用，以实现更大的有效 DP 规模，充分提升设备利用率</span>。这里将生成阶段的并行组记作 $$p_g$$-$$t_g$$-$$d_g$$-$$d$$。

* **<span style="color: rgb(36,91,219); background-color: inherit">工作流程</span>**

在第$$i$$次 RLHF 迭代的训练阶段结束之后、第$$i+1$$次迭代的生成阶段开始之前，<span style="color: rgb(100,37,208); background-color: inherit">需完成模型参数的重分片和 prompt 数据的分发，以适配两个阶段各自的并行组配置</span>。

第$$i+1$$次迭代执行如下步骤：

![](../../images/视觉多模态项目-image-8.png)

> 1. 收集第$$i$$次迭代更新后的策略模型参数，供后续在每个微 DP 组内进行生成
>
> 2. 将一批提示加载到每个模型副本中，执行自回归生成，即 RLHF 的生成阶段
>
> 3) 在每个微 DP 组内部对生成结果执&#x884C;**`all-gather`**&#x64CD;作，汇总输出
>
> 4) 根据训练阶段的三维并行配置，重新划分模型参数
>
> 🍀 5. 在正确重分布模型权重、prompt 和 response 后，计算损失并更新策略模型权重，进入第$$i+1$$次迭代的训练阶段

* **<span style="color: rgb(36,91,219); background-color: inherit">零冗余的模型分片</span>**

在标准 3D 并行中，并行组的构建方式通常如下：

> * **`PP`和`TP`组**：通过连续编号分配给流水线阶段或张量分片
>
> 🍀 * **`DP`组**：&#x6309;**`PP`**`  大小 ×  `**`TP`**` 大小`的步长间隔选取设备编号

> 例如：在下图(a)中，训练阶段使&#x7528;**`1-4-2`**&#x7684;并行配置：
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">PP 组</span>**：所有 GPU 属于一个组
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">TP 组</span>**：**`[G1,G2,G3,G4]`**、**`[G5,G6,G7,G8]`**
>
> * **<span style="color: rgb(36,91,219); background-color: inherit">DP 组</span>**：**`[G1,G5]`**、**`[G2,G6]`**、**`[G3,G7]`**、**`[G4,G8]`**
>
> ![](../../images/视觉多模态项目-image-9.png)

若生成阶段采用不同的配置，&#x5982;**`1-2-2-2`**，且沿用上述常规分组方法，则在从训练切换到生成时，3D-HybridEngine 需先在模型并行组内执&#x884C;**`all-gather`**&#x805A;合全部参数，再根据新并行组保留部分权重。但在某些 GPU 上，&#x5982;**`G2、G3、G6、G7`**，训练与生成的权重无交集，因此必须额外保留训练权重用于后续恢复，这里作者将采用此类常规分组方法的系统称&#x4E3A;**`HybridFlow-V`**。

生成阶段重新组织并行分组后，可以消除权重副本冗余，并缩小训练态切到生成态时的重分片开销。具体策略如下：

> * **`TP`<span style="color: rgb(36,91,219); background-color: inherit">和</span>`PP`<span style="color: rgb(36,91,219); background-color: inherit">组</span>**：按$$\frac{t}{t_g}$$和$$\frac{p}{p_g}$$的间隔选取设备编号
>
> 🍀 * **<span style="color: rgb(36,91,219); background-color: inherit">微</span>`DP`<span style="color: rgb(36,91,219); background-color: inherit">组</span>**：沿 TP 或 PP 维度顺序分配设备编号

> 在上图(b)中，生成阶段使&#x7528;**`1-2-2-2`**&#x914D;置：
>
> * TP 组：**`[G1,G3]`**、**`[G2,G4]`**、**`[G5,G7]`**、**`[G6,G8]`**
>
> * 微 DP 组：**`[G1,G2]`**、**`[G3,G4]`**、**`[G5,G6]`**、**`[G7,G8]`**

<span style="color: rgb(100,37,208); background-color: inherit">这种重构使得每个设备上的训练与生成权重存在重叠，从而可在生成时直接复用训练权重，避免额外内存占用。同时</span>，3D-HybridEngine 在每个微 DP 组内并发执&#x884C;**`all-gather`**，大幅降低通信开销。

4. **<span style="color: rgb(36,91,219); background-color: inherit">切换开销分析</span>**

右表对比了不同策略模型引擎在训练与生成阶段切换时的通信开销与内存占用。假设策略模型大小为$$M$$，共使用$$N_a$$个 GPU。

![](../../images/视觉多模态项目-image-10.png)

> 🍀 **<span style="color: rgb(36,91,219); background-color: inherit">DeepSpeed-Chat</span>** 中的策略模型引擎在切换阶段会在所有 GPU 上执行一次全局&#x7684;**`all-gather`**&#x64CD;作
>
> **<span style="color: rgb(36,91,219); background-color: inherit">HybridFlow-V</span>** 则在训练阶段的 TP 和 PP 组内分别执&#x884C;**`all-gather`**

这两种引擎都需要先在每个 GPU 的内存中聚合完整的模型参数，然后再根据生成阶段的并行组配置重新划分模型状态。因此，<span style="color: rgb(100,37,208); background-color: inherit">模型参数的峰值内存使用量达到完整的</span>$$M$$。由于在某些 GPU 上无法在生成过程中复用训练时的权重，<span style="color: rgb(100,37,208); background-color: inherit">必须保留这些训练权重，从而分别导致 </span>$$\frac{1}{tpd}M$$<span style="color: rgb(100,37,208); background-color: inherit"> 和 </span>$$\frac{1}{tp}M$$<span style="color: rgb(100,37,208); background-color: inherit"> 的额外内存消耗</span>。

而在生成阶段采用我们所设计的并行分组方法后，HybridFlow &#x5C06;**`all-gather`**&#x64CD;作限制在每个微数据并行组内部进行。通信开销降低至：

$$\frac{d_g - 1}{tp} M = \frac{tp - t_g p_g}{t_g p_g tp} M$$

每个 GPU 只需收集其所属微 DP 组内的远程参数，并可在生成过程中直接复用本地的训练权重。因此，<span style="color: rgb(100,37,208); background-color: inherit">HybridFlow 中模型参数的峰值内存使用量恰好等于生成阶段每个 GPU 上的模型分片大小，完全消除了 GPU 内存中的冗余占用</span>。

### 1.2.8 <span style="color: rgb(36,91,219); background-color: inherit">设备映射</span>

混合编程模型要求用户提供以下配置，称为 **<span style="color: rgb(100,37,208); background-color: inherit">RLHF 数据流到设备的映射方案</span>**：

> * 各模型在设备上的部署位置
>
> 🍀 * 每个阶段各模型所采用的并行策略

为此，VeR 提供一个高效算法，帮助用户在给定设备集群上找到最优映射方案，以最小化每次 RLHF 迭代的端到端延迟。给定数据流$$D$$，算法执行如下步骤：

1. **<span style="color: rgb(36,91,219); background-color: inherit">枚举所有可能的部署方案</span>**$$\mathcal{P}$$<span style="color: rgb(36,91,219); background-color: inherit">（第</span>**`3`**<span style="color: rgb(36,91,219); background-color: inherit">行）</span>：例如，<span style="color: rgb(220,155,4); background-color: inherit">PPO 包含</span>**`4`**<span style="color: rgb(220,155,4); background-color: inherit">个模型，共有</span>**`15`**<span style="color: rgb(220,155,4); background-color: inherit">种部署方式</span>，范围从所有模型独立部署，&#x5982;**`OpenRLHF`**，到全部共置于同一组设备，&#x5982;**`DeepSpeed-Chat`**

> 将<span style="color: rgb(100,37,208); background-color: inherit">共置于同一组 GPU 上的模型集合称为一个</span>**<span style="color: rgb(100,37,208); background-color: inherit">共置集</span>**。同一共置集内的模型仍可采用不同的并行策略。

* **<span style="color: rgb(36,91,219); background-color: inherit">确定最小 GPU 分配数</span>**$$A_{\min}$$<span style="color: rgb(36,91,219); background-color: inherit">（第</span>**`9`**<span style="color: rgb(36,91,219); background-color: inherit">行）</span>：基于共置模型的显存需求，计算每个共置集所需的最少 GPU 数量，确保不发生 OOM。

3. **<span style="color: rgb(36,91,219); background-color: inherit">枚举可行的设备分配方案</span>**<span style="color: rgb(36,91,219); background-color: inherit">（第</span>**`10–12`**<span style="color: rgb(36,91,219); background-color: inherit">行）</span>：从$$A_{\min}$$开始，遍历所有可能的设备分配组合。

4. **<span style="color: rgb(36,91,219); background-color: inherit">自动并行优化</span>：**&#x5BF9;于给定的设备分配$$A$$和模型计算负载$$W$$，包括输入输出形状及任务类型：训练/推理/生成，调&#x7528;**`auto_parallel`**&#x6A21;块寻找最优并行策略，最小化执行延迟。该模块依赖一个模拟器 **`simu`**。

5) **<span style="color: rgb(36,91,219); background-color: inherit">计算端到端延迟</span>`d_cost`**<span style="color: rgb(36,91,219); background-color: inherit">（第</span>**`17、25`**<span style="color: rgb(36,91,219); background-color: inherit">行）</span>：遍历数据流图的所有阶段，累加各阶段延迟：

   * 若多个模型属于同一共置集且在同一阶段执行，如训练阶段中策略与价值模型同时更新，则其延迟相加（&#x7B2C;**`32`**&#x884C;）

   * 若模型位于不同共置集，则同阶段可并行执行，阶段延迟取各集合最大值（&#x7B2C;**`33`**&#x884C;）

![](../../images/视觉多模态项目-image-11.png)

6. **<span style="color: rgb(36,91,219); background-color: inherit">选择最优映射方案</span>**<span style="color: rgb(36,91,219); background-color: inherit">（第</span>**`18–23`**<span style="color: rgb(36,91,219); background-color: inherit">行）</span>：找出使每次 RLHF 迭代执行时间最短的设备部署与并行策略组合。

**<span style="color: rgb(222,120,2); background-color: inherit">复杂度分析</span>**

算法最坏时间复杂度为：

$$O\left( \frac{(N-1)!}{(k-1)! (N-k)!} \right)$$

其中$$k$$表示数据流中模型数量，$$N$$表示可用 GPU 总数。该复杂度对应于最坏情况下的<span style="color: rgb(100,37,208); background-color: inherit">独立部署策略，即将</span>$$N$$<span style="color: rgb(100,37,208); background-color: inherit">个设备分配给</span>$$k$$<span style="color: rgb(100,37,208); background-color: inherit">个模型的整数划分问题</span>。

为提升效率，对每个模型在特定设备数$$A$$下已搜索出的并行策略进行缓存，避免在不同部署方案中重复计算。

尽管当前假设所有 GPU 同构，但算法可轻松扩展至异构设备场景，只需&#x5728;**`simu`**&#x548C;**`auto_parallel`**&#x6A21;块中考虑设备差异性。

```python
class MyNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = nn.Linear(100, 1)

    def compute_loss(self, x, y):
        pred = self.linear(x)
        return F.mse_loss(pred, y)

# 定义 Worker，运行在 GPU 上
@ray.remote(num_gpus=1)
class MyNetWorker(Worker):
    def __init__(self):
        super().__init__()
        self.network = MyNet().cuda()

    def compute_network_loss(self, inputs, targets):
        inputs, targets = inputs.cuda(), targets.cuda()
        return self.network.compute_loss(inputs, targets).item()

if __name__ == "__main__":
    ray.init()

    # 创建两个 Worker
    worker0 = MyNetWorker.remote()
    worker1 = MyNetWorker.remote()

    # 生成测试数据并切分
    inputs = torch.randn(16, 100)
    targets = torch.randn(16, 1)
    inputs_split = torch.chunk(inputs, 2)
    targets_split = torch.chunk(targets, 2)

    # 并行计算
    future0 = worker0.compute_network_loss.remote(inputs_split[0], targets_split[0])
    future1 = worker1.compute_network_loss.remote(inputs_split[1], targets_split[1])

    # 收集结果
    loss0, loss1 = ray.get([future0, future1])
    avg_loss = (loss0 + loss1) / 2

    ray.shutdown()
```

> **<span style="color: rgb(222,120,2); background-color: inherit">例</span>**：这里展示一下 VeRL 框架里 **colocate&#x20;**&#x7684;效果，把多个 **worker**，&#x5373;**`Actor`**&#x548C;**`Critic`**&#x7ED1;定到同一个 **WorkerDict&#x20;**&#x4E2D;，然后在同一个 Ray 节点上共存运行，最后分别调用它们的方法。

> ```python
> import ray
> import torch
>
> from verl.single_controller.base import Worker
> from verl.single_controller.base.decorator import register, Dispatch
> from verl.single_controller.ray.base import (
>     RayResourcePool, RayClassWithInitArgs, 
>     RayWorkerGroup, create_colocated_worker_cls
> )
> from verl import DataProto
>
>
> # 定义一个 Actor Worker，执行加法操作
> @ray.remote
> class Actor(Worker):
>     def __init__(self):
>         super().__init__()
>
>     @register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)
>     def add(self, data: DataProto):
>         # 把 tensor 放到 cuda 上，并加上当前 worker 的 rank
>         data.batch['a'] = data.batch['a'].to("cuda")
>         data.batch['a'] += self.rank
>         return data
>
>
> # 定义一个 Critic Worker，执行减法操作
> @ray.remote
> class Critic(Worker):
>     def __init__(self, config):
>         super().__init__()
>         self.config = config
>
>     @register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)
>     def sub(self, data: DataProto):
>         # 把 tensor 放到 cuda 上，并减去配置中的参数
>         data.batch['a'] = data.batch['a'].to("cuda")
>         data.batch['a'] -= self.config['b']
>         return data
>
>
> def test_colocated_workers():
>     ray.init()
>
>     # 构造输入数据：维度为10的全零向量
>     data = DataProto.from_dict({'a': torch.zeros(10)})
>     print("Input:", data.batch["a"])
>
>     # 封装 Actor 和 Critic 类及其初始化参数
>     actor_cls = RayClassWithInitArgs(cls=Actor)
>     critic_cls = RayClassWithInitArgs(cls=Critic, config={'b': 10})
>
>     # 构建仅含一个节点（2GPU）的资源池
>     resource_pool = RayResourcePool(process_on_nodes=[2])
>
>     # 利用 create_colocated_worker_cls 把 Actor 和 Critic 绑定到同一个 WorkerDict 上
>     cls_dict = {'actor': actor_cls, 'critic': critic_cls}
>     ray_cls_with_init = create_colocated_worker_cls(cls_dict)
>
>     # 打印元信息，确认 worker 确实绑定到 WorkerDict
>     print(type(ray_cls_with_init))  # RayClassWithInitArgs
>     print(ray_cls_with_init.cls.__ray_actor_class__)      # WorkerDict
>     print(ray_cls_with_init.cls.__ray_actor_class__.__base__)  # Worker
>     print(ray_cls_with_init.cls.actor_add)     # Actor的 add 方法
>     print(ray_cls_with_init.cls.critic_sub)    # Critic 的 sub 方法
>
>     # 启动 WorkerDict，并获取 actor 和 critic 对应的 worker group
>     wg_dict = RayWorkerGroup(resource_pool=resource_pool, ray_cls_with_init=ray_cls_with_init)
>     spawn_wg = wg_dict.spawn(prefix_set=cls_dict.keys())
>     actor_wg, critic_wg = spawn_wg['actor'], spawn_wg['critic']
>
>     # 执行 Actor 的 add 和 Critic 的 sub 操作
>     actor_output = actor_wg.add(data)
>     critic_output = critic_wg.sub(data)
>
>     # 预期结果：actor_output: 前 5 个为 0，后 5 个为 1，critic_output: 全为-10
>     print("Actor output:", actor_output.batch["a"])
>     print("Critic output:", critic_output.batch["a"])
>
>     ray.shutdown()
>
> if __name__ == '__main__':
>     test_colocated_workers()
> ```

## 1.3 <span style="color: rgb(36,91,219); background-color: inherit">LlamaIndex</span>

LlamaIndex 可以让 LLM 连接到私有的、异构的数据源，如 PDF、数据库、API 等。它的核心作用是构建 **RAG**。大体来说，LlamaIndex 的工作流有五个重要步骤：<span style="color: rgb(100,37,208); background-color: inherit">加载 Loading</span>、<span style="color: rgb(100,37,208); background-color: inherit">解析 Parsing</span>、<span style="color: rgb(100,37,208); background-color: inherit">索引 Indexing</span>、<span style="color: rgb(100,37,208); background-color: inherit">存储 Storing</span> 和 <span style="color: rgb(100,37,208); background-color: inherit">查询 Querying</span>。一个简单的 RAG 链路伪代码如下：

```python
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

# 1. 加载文档
documents = SimpleDirectoryReader("./data").load_data()

# 2. 创建索引
index = VectorStoreIndex.from_documents(documents)

# 3. 创建查询引擎并提问
query_engine = index.as_query_engine()
response = query_engine.query("LlamaIndex 的使用方法有哪些？")
```

下面详细展开各个功能：

### 1.3.2 <span style="color: rgb(36,91,219); background-color: inherit">文档解析</span>

在 LlamaIndex 的工作流中，需要将原始文&#x6863;**`Document`**&#x8F6C;化为可索引单&#x5143;**`Node`**&#x7684;，解析的核心目标有两个：

> 1. **<span style="color: rgb(36,91,219); background-color: inherit">切分数据</span>**：确保文本片段符合 LLM 的上下文窗口
>
> 📍 2. **<span style="color: rgb(36,91,219); background-color: inherit">保留结构</span>**：尽量不切断句子、段落或语义单元，并提取标题、页码等元数据

1. **<span style="color: rgb(36,91,219); background-color: inherit">句子切分器 SentenceSplitter</span>**

这是最平衡的选择。它会优先在段落分隔符处切分，其次是句子，最后才是字符，从而尽可能保持语义完整：

```python
from llama_index.core import SimpleDirectoryReader
from llama_index.core.node_parser import SentenceSplitter

# 加载文档
documents = SimpleDirectoryReader("./data").load_data()

# 定义解析器
parser = SentenceSplitter(
    chunk_size=512,                  # 每个片段的最大 Token 数
    chunk_overlap=50,                # 片段间的重叠量，防止语义断层
    separator=" ",                   # 次级分隔符
    paragraph_separator="\n\n\n",    # 优先级最高的分隔符
)

# 获得节点
nodes = parser.get_nodes_from_documents(documents)

print(f"生成的第一个片段内容: {nodes[0].text}")
```

* **<span style="color: rgb(36,91,219); background-color: inherit">Token 切分器 TokenTextSplitter</span>**

严格按照 Token 数量切分，不考虑句子边界。适合对 Token 消耗极其敏感的场景。

```python
from llama_index.core.node_parser import TokenTextSplitter

parser = TokenTextSplitter(chunk_size=256, chunk_overlap=20)
nodes = parser.get_nodes_from_documents(documents)
```

* **<span style="color: rgb(36,91,219); background-color: inherit">基于特定格式 Markdown/HTML/JSON 解析</span>**

### 1.3.5 <span style="color: rgb(36,91,219); background-color: inherit">查询链路</span>

> ⚽ 在 LlamaIndex 中，查询不仅是 **搜索+回答**，而是一个完整的流程。我们可以将查询过程分解为三个核心阶段：**<span style="color: rgb(100,37,208); background-color: inherit">检索 Retrieval</span>**、**<span style="color: rgb(100,37,208); background-color: inherit">后处理 Post-processing</span>** 和 **<span style="color: rgb(100,37,208); background-color: inherit">回答合成 Response Synthesis</span>**。

当调&#x7528;**`query_engine.query("...")`**&#x65F6;，后台发生了以下过程：

> 1. **<span style="color: rgb(36,91,219); background-color: inherit">Query 转换</span>**：将原始问题转化为更适合搜索的向量或子问题
>
> 2. **<span style="color: rgb(36,91,219); background-color: inherit">检索 Retrieval</span>**：从索引中找到最相关&#x7684;**`Nodes`**&#x6587;本块
>
> 3. **<span style="color: rgb(36,91,219); background-color: inherit">后处理 Post-processing</span>**：对检索到的节点进行重排、过滤或精简
>
> 4. **<span style="color: rgb(36,91,219); background-color: inherit">回答合成 Response Synthesis</span>**：将节点内容发给 LLM，生成最终答案

最常用的封装方式，一行代码涵盖了上述所有步骤：

```python
# 默认用法：向量搜索 + 默认总结
query_engine = index.as_query_engine()
response = query_engine.query("LlamaIndex 的核心组件有哪些？")

print(response.response)        # 文本回答
print(response.source_nodes)    # 查到了哪些原始片段
```

为了获得更好的效果，我们通常需要手动配置每个阶段：

1. **<span style="color: rgb(36,91,219); background-color: inherit">检索阶段：决定找得准不准</span>**

可以设置检索多少个片&#x6BB5;**`similarity_top_k`**：

```python
from llama_index.core import VectorStoreIndex, get_response_synthesizer
from llama_index.core.retrievers import VectorIndexRetriever

# 1. 定义检索器：只找最相关的 3 个片段
retriever = VectorIndexRetriever(
    index=index,
    similarity_top_k=3,
)
```

* **<span style="color: rgb(36,91,219); background-color: inherit">后处理阶段：决定留哪些</span>**

最常见的用法是 **<span style="color: rgb(100,37,208); background-color: inherit">Rerank 重排</span>**，Retriever 靠向量距离找内容，但 Reranker 可以用更强的模型判断相关性：

```python
from llama_index.core.postprocessor import SimilarityPostprocessor, KeywordNodePostprocessor

# 只保留相似度得分大于 0.7 的节点，且排除包含 "广告" 字样的节点
node_postprocessors = [
    SimilarityPostprocessor(similarity_cutoff=0.7),
    KeywordNodePostprocessor(exclude_keywords=["广告", "推广"])
]
```

* **<span style="color: rgb(36,91,219); background-color: inherit">回答合成阶段：决定怎么答</span>**

可以决定 LLM 是分步阅读片&#x6BB5;**`Refine`**，还是聚在一起回&#x7B54;**`Compact`**：

```python
# 定义合成器
response_synthesizer = get_response_synthesizer(
    response_mode="compact" # 常用模式，将多个 Node 组合在一起发送给 LLM
)
```

* **<span style="color: rgb(36,91,219); background-color: inherit">完整组装</span>**

将上述组件组装成一个自定义&#x7684;**`QueryEngine`**：

```python
from llama_index.core.query_engine import RetrieverQueryEngine

# 组装自定义查询引擎
custom_query_engine = RetrieverQueryEngine(
    retriever=retriever,
    node_postprocessors=node_postprocessors,
    response_synthesizer=response_synthesizer,
)

# 执行查询
response = custom_query_engine.query("LlamaIndex 的核心组件有哪些？")
```

### 1.3.6 <span style="color: rgb(36,91,219); background-color: inherit">完整流程</span>

这个示例涵盖了：<span style="color: rgb(100,37,208); background-color: inherit">1. 复杂 PDF 解析、2. 语义分块、3. 元数据提取、4. Chroma 向量数据库持久化、5. 带重排 Rerank 的查询引擎</span>：

```python
import os
from llama_index.core import (
    VectorStoreIndex, 
    SimpleDirectoryReader, 
    StorageContext, 
    Settings,
    get_response_synthesizer
)
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core.extractors import TitleExtractor
from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.postprocessor import LLMRerank
from llama_index.core.query_engine import RetrieverQueryEngine
from llama_index.vector_stores.chroma import ChromaVectorStore
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding
import chromadb

# 1. 全局配置，设置模型（确保已设置环境变量 OPENAI_API_KEY）
Settings.llm = OpenAI(model="gpt-4o", temperature=0.1)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")

def run_full_pipeline():
    # 2. 数据加载 Loading
    reader = SimpleDirectoryReader(input_dir="./my_docs", recursive=True)
    documents = reader.load_data()

    # 3. 数据解析与处理
    pipeline = IngestionPipeline(
        transformations=[
            # 语义分块或句子分块
            SentenceSplitter(chunk_size=512, chunk_overlap=50),
            # 自动提取文档标题，增强检索相关性
            TitleExtractor(nodes=5, llm=Settings.llm),
        ]
    )
    # 生成处理后的节点 Nodes
    nodes = pipeline.run(documents=documents)

    # 4. 持久化存储 Storing
    # 初始化本地 ChromaDB
    db = chromadb.PersistentClient(path="./chroma_db")
    chroma_collection = db.get_or_create_collection("full_pipeline_demo")
    
    # 构建向量存储上下文
    vector_store = ChromaVectorStore(chroma_collection=chroma_collection)
    storage_context = StorageContext.from_defaults(vector_store=vector_store)
    
    # 构建索引
    index = VectorStoreIndex(
        nodes, 
        storage_context=storage_context,
        show_progress=True
    )

    # 5. 高级查询引擎构建 Querying
    # 配置检索器，取相关度最高的 10 个片段
    retriever = index.as_retriever(similarity_top_k=10)
    
    # 配置回答合成器
    response_synthesizer = get_response_synthesizer(response_mode="compact")
    
    # 引入重排 Rerank
    # 先找 10 个相似的，再用 LLM 选出其中最相关的 3 个，提升准确率
    reranker = LLMRerank(top_n=3)

    # 组装最终引擎
    query_engine = RetrieverQueryEngine(
        retriever=retriever,
        response_synthesizer=response_synthesizer,
        node_postprocessors=[reranker]
    )

    # 6. 执行查询
    question = "LlamaIndex 的使用方法是什么？"
    response = query_engine.query(question)
    print(f"问题: {question}")
    print(f"回答: {response}")
 
    for i, node in enumerate(response.source_nodes):
        print(f"[{i+1}] (得分: {node.score:.4f}): {node.text[:100]}...")

if __name__ == "__main__":
    run_full_pipeline()
```

### 1.4.2 <span style="color: rgb(36,91,219); background-color: inherit">模型调用</span>

后续调用共享同一 `model` 接口；切换后端时，先回归 Message、stream、batch 和 structured output 四类行为。

1. **<span style="color: rgb(36,91,219); background-color: inherit">LangChain Message 消息格式</span>**

在 LangChain 1.0 中，Message（消息）是模型交互的最基本单元。它既代表模型接收到的输入（Input），也代表模型生成的输出（Output）。

每一轮与大模型的对话，都由一条或多条 Message 构成。每个 Message 不仅包含文字内容，还携带描述上下文状态的元信息（metadata），用于保持对话的一致性和可追踪性。通过这种结构化方式，LangChain 可以让模型在多轮交互中理解“谁在说话”“说了什么”“这条信息属于哪一轮对话”。

| **字段**            | **说明**                                                        | **示例**                                               |
| ----------------- | ------------------------------------------------------------- | ---------------------------------------------------- |
| **Role（角色）**      | 指明消息的类型或来源。常见的有：`system`（系统提示）、`user`（用户输入）、`assistant`（模型回复） | `"role": "user"`<br />                               |
| **Content（内容）**   | 消息的实际内容，可包含文本、图像、音频、文档等多模态数据                                  | `"content": "你好，请帮我总结以下段落。"`                         |
| **Metadata（元数据）** | 可选字段，存储额外信息，如：消息ID、响应时间、token消耗量、消息标签等                        | `"metadata": {"message_id": "abc123", "tokens": 54}` |

LangChain1.0 中提供了跨模型统一的 Message 标准，无论你使用的是 OpenAI、Gemini 还是本地模型，都能保持一致的行为，将消息格式自动对齐。

### 1.4.3 <span style="color: rgb(36,91,219); background-color: inherit">结构化输出</span>

结构化输出是服务合同，不是提示词装饰。Schema 负责字段类型和必填约束，业务层还要验证证据、权限和状态转换。

1. **<span style="color: rgb(36,91,219); background-color: inherit">Pydantic</span>**

其中Pydantic 提供字段校验、默认值、描述信息、多层嵌套等高级能力，是生产场景首选。

```python
from pydantic import BaseModel, Field

class Movie(BaseModel):
    """A movie with details."""
    title: str = Field(..., description="电影名称")
    year: int = Field(..., description="电影发布年份")
    director: str = Field(..., description="电影的导演")
```

这里使用 Pydantic 的 BaseModel 定义一个严格的数据结构。每个字段都明确了类型（如 str、int、float），并用 Field(..., description="...") 提供语义描述，其中... 的作用就是在模型回复时，LangChain 会要求 LLM 的输出必须能填充这些字段。

然后使用 with\_structured\_output 即可引导模型进行结构化输出：

```python
model_with_structure = model.with_structured_output(Movie)
response = model_with_structure.invoke("请介绍电影《泰坦尼克号》")

print(type(response))

print(response.year)
print(response.director)
```

### 1.4.5 <span style="color: rgb(36,91,219); background-color: inherit">工具调用</span>

`create_agent()` 负责组装模型节点、工具节点和状态传递。工程上要额外限制工具白名单、超时、重试、幂等和审计日志。

* 节点（Node）：代表执行步骤，例如模型调用节点、工具执行节点或中间件节点

* 边（Edge）：代表执行流程与状态流转

* 图（Graph）：定义了 Agent 如何在这些节点之间流动、推理和决策。

所以 LangChain 的每个 Agent 都是一张有向图，**语言模型是推理引擎，工具是行动节点，而底层则是通过LangGrph进行的编写和实现**。

```python
def get_weather(loc):

    url = "https://api.openweathermap.org/data/2.5/weather"

    # Step 2.设置查询参数
```

普通函数封装成 Tool 后，函数名、参数类型、字段说明和返回结构都会进入模型上下文。描述不清会直接增加错调和漏调。

```python
from langchain.tools import tool

@tool
def get_weather(loc: str):
    """
    查询即时天气函数
    :param loc: 必要参数，字符串类型，用于表示查询天气的具体城市名称，\
    注意，中国的城市需要用对应城市的英文名称代替，例如如果需要查询北京市天气，则loc参数需要输入'Beijing'；
    :return：OpenWeather API查询即时天气的结果，具体URL请求地址为：https://api.openweathermap.org/data/2.5/weather\
    返回结果对象类型为解析之后的JSON格式对象，并用字符串形式进行表示，其中包含了全部重要的天气信息
    """
    # Step 1.构建请求
    url = "https://api.openweathermap.org/data/2.5/weather"

    # Step 2.设置查询参数
    params = {
        "q": loc,               
        "appid": os.getenv("OPENWEATHER_API_KEY"),    # 输入API key
        "units": "metric",            # 使用摄氏度而不是华氏度
        "lang":"zh_cn"                # 输出语言为简体中文
    }

    # Step 3.发送GET请求
    response = requests.get(url, params=params)
    
    # Step 4.解析响应
    data = response.json()
    return json.dumps(data)
```
